# 01 简要整体方案

> 本篇回答三个问题：真正要解决的业务问题是什么、平台与现场设备及人员的职责边界在哪、一期做和暂缓什么。所选的一期核心业务闭环（番茄智轨产线批次执行）在 [02_核心闭环设计.md](02_核心闭环设计.md) 单独展开。

## 1. 真正要解决的业务问题

公司要建的不是"多几个软件界面"，而是一条**从生产目标到现场执行反馈的可运行链路**。在没有平台的状态下，这条链路存在三个断点：

| 断点 | 现状（无平台时的典型做法） | 后果 |
| --- | --- | --- |
| 目标 → 计划 | 销售、展示、科研对产出的要求停留在口头或表格 | 无法结构化为批次与计划，事后无法检验目标是否达成 |
| 计划 → 设备 | 环境、水肥要求靠人工抄录到各控制器，每套设备各接各的 | 换设备就换一套做法，经验无法沉淀为可复用的产品资产 |
| 执行 → 反馈 | 作业结果、异常、产量留在纸面或人脑 | 复盘、经营分析、参观讲解都没有可靠依据，问题无法追溯 |

Greenhouse OS 一期的定位就是补齐这条链路中**最小可运行的部分**：把生产目标翻译成"作物批次 + 生产计划 + 环境/水肥目标带 + 作业任务"，把任务的"下发—执行—反馈"接到现场，把结果、异常和人工决策结构化地记录下来。

一期**明确不追求"智能"**：AI 按一个可替换插件通道接入，只有"采收排产预测"一个能力真实进入业务链路（且仅作排产参考、经人工确认才成轮次计划）；"异常处置建议"能力一期只做**影子运行**（建议照常生成、留档评估准确率，但不进入审定与下发队列）。插件失效时采收改人工报数、异常改规则预案 + 人工授权，闭环运行不受影响。这与题面要求一致——模型建议需经适用条件、约束和授权检查，失效时依靠已验证规则和人工授权维持基础运行。

## 2. 平台与现场设备、人员的职责边界

| 层 / 角色 | 承担 | 明确不承担 |
| --- | --- | --- |
| **Greenhouse OS**（决策协调层，本期建设） | 批次、计划、目标带、任务的管理与编排；状态汇聚与运行证据留存；异常升级与人工授权流程；向 AI 插件提供上下文并校验其建议 | 不做实时控制；不做安全互锁；不直接驱动执行机构；不在控制器失联时越权代管现场 |
| **现场自动化层**（气候电脑、PLC、水肥控制器、智轨/产线控制器） | 实时执行；安全互锁；故障保护；断网自治；手动旁路 | 不理解"批次/计划"业务语义，只认标准化的目标带/任务报文 |
| **AI 插件**（可替换） | 采收排产/产量预测（一期启用，仅作参考）；异常处置建议（一期影子运行，只留档不下发）；统一输出"建议 + 置信度 + 适用条件（含品种、生育期）" | 不直接下发任何指令；启用类输出必须经平台约束校验与授权检查；插件失效不影响闭环 |
| **种植工程师** | 维护作物工艺模板（环境带、EC 靶标）；审定目标带；异常处置决策 | —— |
| **现场操作员** | 执行作业任务并如实反馈；报告现场异常 | 不擅自修订已生效的目标带 |
| **自动化工程师** | 设备接入、维护、离线处置 | 不修改业务计划 |

边界设计沿用第一题已验证的原则：平台对"**受理—计划—事件—证据**"负责，**计划完成不等于设备已执行**；所有下行指令带版本号保证幂等，重复下发返回已知结果而非产生新动作；所有状态变化留事件，事件带序号、时间戳与责任主体。这套语义在第一题中已通过公开检查器验证（duplicate / conflict / 事件归属一致性），将直接沉淀为 Greenhouse OS 任务与目标带模型的基础。

## 3. 一期范围取舍

**一期做：**

- 番茄智轨产线**批次执行闭环**全链路（详见 02 篇），它覆盖平台全部核心对象：作物批次、生产计划、环境/水肥目标带、作业任务、采收轮次、异常、人工授权。
- **设备适配器框架 + 三个模拟器**（气候电脑、水肥控制器、智轨机器人调度）：无真机时闭环可完整联调，真机接入只替换适配器。
- **一个 AI 插件通道、两个受限能力**：采收排产预测启用（含置信度与适用条件，人工确认才成轮次计划）；异常处置建议一期影子模式（只生成留档、不进审定下发队列）；同步验证停用插件时的降级路径。
- **运行证据查询**：批次时间线、任务台账、异常台账、授权记录，支撑复盘与参观讲解（讲解功能本身不做，只保证记录可用）。

**一期暂缓（含理由）：**

| 暂缓项 | 理由 |
| --- | --- |
| 叶菜/芽苗产线全量接入 | 仅验证对象模型兼容、工艺参数走配置模板；等番茄产线跑通后再复制，避免两条产线同时改动基础模型 |
| 采后包装与商品交付细化流程 | 一期只固化"采收轮次确认"这一个交接点，包装线内部流程属另一专业域 |
| 经营分析看板、参观讲解系统 | 消费同一批记录，属于数据展示层，不阻塞闭环，二期基于真实运行数据设计更准 |
| AI 环境寻优、能耗优化 | 等"建议—校验—授权"管道（含一期影子运行的准确率评估）被验证可靠后再评估，避免未验证模型进入控制链路 |
| 数字孪生、多温室配置化复用 | 属于沉淀期工作，首个项目跑通后才有沉淀的原料 |

取舍理由一句话：**一期的目标不是功能多，而是把一条闭环跑真**——真批次、真下发、真回执、真反馈、真异常、真授权。其余业务都建在这条地基上；地基不真，功能越多越难收敛。

## 4. 与其他业务的必要联系

- **上游（种苗/育苗接口与定植）**：本闭环定义了"批次创建"接口——种苗验收信息（品种、数量、苗龄、健康状态）作为批次档案的一部分进入系统，定植任务完成即批次进入 growing。种苗环节的细化（催芽、发芽率统计）一期不做。
- **下游（采收交接与采后包装）**：本闭环定义了"采收轮次确认"接口——每轮采收的产量、分级、筐数经现场确认后即视为向包装线的交接凭证。包装线内部调度不在一期。
- **横向（叶菜/豆芽多叠域产线）**：复用同一套对象模型与状态机，差异只在工艺模板（环境带、EC 靶标、生育期定义）与设备能力清单，走配置而非新代码。一期不实施，但建模时预留。

## 5. 已知事实、设计假设与待确认事项

**已知事实**（来自题面）：平台定位为决策协调层；现场自动化层已具备自治与保护能力；两条产线与展示中心用途；模型按可替换插件接入。

**设计假设**（影响设计、待现场验证；每条说明答案变化后受影响的部分）：

- **A1 智轨产线设备具备标准消息接口**（任务下发、进度回报、完成/异常事件、回执）。
  若不成立 → 在适配器层增加本地网关做协议转换与缓存，闭环逻辑与对象模型不变；工期风险集中在适配器。
- **A2 现场控制器接受"目标带"粒度**（指标上下限 + 生效窗口），而非仅接受固定设定点。
  若不成立 → 目标带降级为"设定点 + 预警阈值"下发，闭环语义（版本化、回执、偏离事件）全部保留，仅报文字段变化。
- **A3 首期番茄按轮次连续采收**（每 3-4 天一轮）。有公开行业依据（见 02 篇调研核查判断 1），但仍需按芯鲜派品种与销售模式确认。
  若实际为一次性采收品种 → 采收轮次对象简化为单次事件，批次状态机不变。

**待确认事项**（谁提供什么，未确认前方案如何成立）：

| 事项 | 谁确认 | 未确认时方案如何成立 |
| --- | --- | --- |
| 智轨设备实际接口协议与能力清单 | 自动化/项目组 | 用模拟器按 A1 假设先行推进全部闭环设计与联调，真机只替换适配器 |
| 番茄品种、目标市场与采收成熟度标准 | 种植工程师 | 成熟度标准建模为采收轮次的可配置字段，默认按 breaker/turning 分级 |
| 环境/水肥工艺模板数值（温度带、EC 靶标） | 种植工程师 | 平台不写死任何农业数值，全部作为工艺配置；未确认前用公开资料区间占位并标注 |
| 首期批次规模与产线槽位数量 | 项目组 | 对象模型与规模无关；仅影响模拟器数据量 |
